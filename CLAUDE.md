## Mission

Build a local AI engineering assistant for SY Gelliceaux (Southern Wind 108 hybrid sailing yacht). Phase 1 is a working troubleshooting agent on the engineer's MacBook. Phase 2 is a multi-tenant cloud platform for the superyacht industry. Build everything Phase-1 in a way that lifts cleanly to Phase-2.

The Phase 1 brief lives in this project's parent Claude.ai project. Treat it as authoritative for scope.

- The user is a working marine engineer with **zero coding experience**. He directs, you build.
- **Ruthless mentor mode.** If a plan is weak, say why. Stress-test. No reflexive validation.
- **Scope discipline.** Build one thing well before adding the next. No scope creep.
- **Honesty over agreement.** If documentation is wrong, say so. If a design is fragile, say so.
- Concise. Engineer briefing colleague, not professor lecturing student. Numbered steps. Cite sources.

## Architecture rules — NON-NEGOTIABLE

1. **Model-agnostic.** Every external service (LLM, embeddings, vector store, comms transport) sits behind an abstract interface in `providers/`. Code outside `providers/` never imports a vendor SDK. Swapping providers = one env var change.

2. **No writes to vessel systems. Ever.** The agent reads from Exocet, never writes. Fire and bilge systems are isolated and never queried.

3. **Read-only data tap.** Live data via the Exocet HTTP `/data` endpoint and websocket on `192.168.1.101`. One poll per minute baseline (websocket preferred when in use).

4. **Vessel-specific facts in the system prompt, not retrieval.** Critical disambiguations (see Locked Facts below) go directly into the system prompt — too important to leave to retrieval probability.

5. **Citations always.** Every claim from a document must cite the source. The agent says "I don't know" cleanly when retrieval is empty.

6. **Token discipline.** Tight system prompt (<500 tokens). Pre-filtered retrieval. Compressed conversation history after 3-4 turns. See Phase 1 brief Section 11 for the full budget.

## Locked vessel facts — go directly into the system prompt

These are vessel truths that no manual will spell out the way an engineer who has run the system understands them. The system prompt MUST include all of these, verbatim or near-verbatim.

### Propulsion

> Single AC Traction Motor (ACTM — BAE GPM-12). Direct-drive, gearless, oil-less. 205 kW cont / 300 kW peak; 2000 Nm cont / 3700 Nm peak. Water-glycol cooled, IP67. Authoritative source: CS-21-D82 (GPM-12 datasheet). "HDS 200" is a different BAE variant — NOT a GPM-12 synonym. The HybriGen Maintenance Manual (M50GB3822) does NOT cover the GPM-12; its oil, filter, and gearbox schedules do not apply. GPM-12 maintenance = coolant / cooling system only.
> Fed and controlled by one of two interchangeable MPCS units (MPCS_P port, MPCS_S starboard) selected via the HVPDU S2 switch. HVPDU S1 switch separates port/starboard HV DC buses for fault isolation. Only one MPCS connects to the ACTM at any time. Exocet `BAE_Motor_*_pt` and `_stbd` channels indicate which MPCS is currently driving — non-zero values appear on the active side. Both channels showing simultaneous load = fault condition. Authoritative source: BAE document CM-22-702 HVPDU Requirements.

### BEL crash history (grounding / CAN bus)

> Two investigations; CM-26-2024 is current and authoritative. CM-24-1732 (earlier): ACTM grounding 16 A to ground bar → CAN bus noise → BEL crashes; fix = separate ground lines ACTM→each MPCS. CM-26-2024 (April 2026): actual root cause = BEL sync signal corruption — sync reference wired to BEL chassis (CAN GND) instead of BEL RTN (PIN 7); GPM-12 ground-plane noise corrupted the sync signal. CAN noise was the initial hypothesis and was ruled out. Four corrective actions: (1) sync ref reconnected to BEL RTN/PIN 7; (2) all bonding connections cleaned; (3) PORT+STBD MPCS grounds relocated to same busbar terminal as GPM-12; (4) additional grounding cables GPM-12↔PORT MPCS and GPM-12↔STBD MPCS. Outstanding issues (§6, unresolved April 2026): BEL overloading — 50 A peaks per BEL during nominal AUX load, tripping breakers; GPM-12 alignment — motor orbits the main shaft, threatens input bearing and Hundested gearbox.

### EMRAX disambiguation

> EMRAX1 and EMRAX2 in Exocet sensor data refer to the **MYT hydraulic powerpack motors** (Emrax 268). They are NOT the propulsion motor. Confusing them when diagnosing propulsion faults gives wrong diagnostic direction.

### Exocet = Pixel Sur Mer (the data source)

> "Exocet" is the product made by **Pixel Sur Mer**. It is the onboard data aggregator: it taps every CAN bus and network aboard (hydraulic load cells, B&G network, propulsion/BAE) and summarises them into one local source on the vessel network. This is the `192.168.1.101/data` endpoint the agent reads. The agent samples it every minute (or less) to monitor behaviours, track trends, and flag when something is out of normal range. Manual ingested under 900 Miscellaneous (it doesn't map to a single system). Core to the sensor-poller (Block 4.3) and a likely v2 architecture pivot.

### Timestamps

> Use `GNSS_UTCdate` and `GNSS_UTCtime` as the authoritative timestamp source. The SBG IMU clock is unset and reports `2015-05-03` consistently — never use SBG timestamps.

## Tech stack — Phase 1

- **Language:** Python 3.12
- **LLM:** Anthropic Claude (model: `claude-sonnet-4-6`) via abstract `LLMProvider`
- **Embeddings:** Voyage AI (`voyage-3`, 1024 dims) via abstract `EmbeddingProvider`
- **Vector DB:** ChromaDB local (when added)
- **Document parsing:** pypdf, python-docx (when added)
- **Comms:** Twilio WhatsApp Sandbox in Phase 1, Meta Business API in Phase 2 (abstracted behind `MessagingProvider`)
- **Sensor data:** Exocet `/data` HTTP endpoint + websocket; pre-processor summarizes raw arrays before any context is sent to the LLM

## Working principles for code

- **Type hints everywhere.** This is a multi-component system; types catch errors early.
- **Docstrings on public functions.** Brief, useful, no padding.
- **Errors fail loud and clear.** No silent fallbacks for missing API keys, malformed data, or unexpected schemas.
- **No magic globals.** Configuration comes from `config.py` or `.env`. Functions take their inputs as arguments.
- **Tests where they earn their place.** Smoke tests for integrations. Unit tests for parsers and pre-processors. Don't test framework code.
- **A validation gate must exercise the REAL dispatcher path, not a shortcut around it.** Twice a gate passed clean while bypassing the call path a real run actually uses: (1) Block C — `parse_xlsx` validated on row-1-header sheets, but the real Lanzarote sheet had a blank row 1 → 0 chunks; (2) Block D — vision validated by calling `describe()` directly, which skipped `route_kind`, whose missing `import re` then failed *every* file on the first real burn. Before trusting a validation, ask explicitly: **does this test the real dispatch path, or a convenient shortcut?** [standing question for the D retro]
- **Logging over print** in anything beyond a smoke test. Use Python's `logging` module, write to `logs/`.
